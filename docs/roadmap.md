# AI Manga Viewer 開発方針

2026-10-02時点。現在0.3.0。日程や将来の版番号を固定せず、実機検証と利用者の反応で更新する。

Phase 1.5〜2の安定化を経て、Phase 3の全画面・自由ズーム・パンを専用テストサイトで確認し、追加Aとして1ページ・見開き・自動のページレイアウトをローカル実装した。Phase 4のManga Library・1冊参照基盤と、Phase 5のCTA最小実装をローカルで進行中。Phase 6は漫画解析の識別キー、Viewer表示、ブラウザー内イベント、既定OFFのREST・DB保存基盤、有効閲覧時間、匿名読者と30分以内の再開判定、最小集計画面までローカル実装した。Phase 7Aは外部AIへ送信せず、相談テーマ・Viewer設定・集計結果・画像URLをMarkdownへ整理してコピーする基盤をローカル実装し、初回実証を受けてページ間の到達減少とスマホで実際に使われるコマ設定が正しく伝わるVersion 2へ更新した。Phase 8AではFree / Proの製品境界と停止時の安全なフォールバックを正式化した。安定化は[Phase 2検証記録](phase-2-validation.md)、通常閲覧は[Phase 3検証記録](phase-3-validation.md)、登録基盤は[Phase 4検証記録](phase-4-validation.md)、CTAは[Phase 5検証記録](phase-5-validation.md)、解析は[Phase 6設計方針](phase-6-analytics-design.md)、AI相談は[Phase 7A設計方針](phase-7-consultation-design.md)、製品境界は[Phase 8A Free / Pro製品設計](phase-8-free-pro-design.md)を参照する。

## 商品の価値

AIで作った漫画をWordPressで綺麗に読ませる。通常漫画・企業紹介・冊子にも使える。漫画の公開・閲覧機能はFree/Core、コマ読み・CTA・Analytics・AI相談はPro Add-onとして分離する。

Freeは読者自身が拡大・移動して快適に読める通常ビューアーと公開基盤、Proは作者がコマの位置・順序・倍率を指定し、誘導・分析・改善まで行う機能群とする。無料側の自由ズームを充実させ、コマ読みをProの強みとして磨く。初期の製品境界と停止時挙動は[Phase 8A仕様](phase-8-free-pro-design.md)を基準とし、将来機能は実装前に個別評価する。

当面は漫画の公開・読書体験を中心に開発する。採用基準は「漫画を公開しやすくするか、読みやすくするか」。通常閲覧とコマ送りを優先し、漫画以外への用途拡張は保留する。登録済み漫画とショートコードは漫画の公開先を広げる機能として開発順序に組み込む。編集は既存ブロックを共用し、Classic Editor専用の別編集機構は作らない。PDF、図面・フロアマップ向けの専用対応は引き続き保留し、着手時期は未定とする。

## 現在の実装と設計の出発点

0.3.0は直接編集用の`ai-manga-viewer/viewer`と参照表示用の`ai-manga-viewer/library-viewer`を持つAPI v3の動的ブロック構成。index.jsのsaveはnullで、直接編集の設定は投稿本文のブロックコメント内のattributesに保存され、PHPのrender_callbackで表示される。管理用CPT `amv_viewer`、1冊用ショートコード、表紙から登録済みViewerを選ぶブロックの基盤は追加済みだが、PDF入力、表示モード選択、複数冊一覧はまだない。

18属性は`pages`、`binding`、`maxWidth`、`showPageNumbers`、`enableEdgeClick`、`showGuideArrowOnAllPages`、`enableAnimation`、`scrollAssist`、`scrollAssistPosition`、`scrollAssistStrength`、`focusReader`、`mobileFocusReader`、`focusReaderStartAtCurrent`、`enableFullscreen`、`enableZoom`、`zoomControlsPosition`、`viewerKey`、`instanceKey`。pages内には画像のid/url/alt/thumbnailUrl、focusAreas/mobileFocusAreas、永続的なpageKey、任意のCTA設定とctaKeyを保持する。align/anchor等のブロックサポート由来の設定も互換対象に含める。

画像のidはメディア添付IDであり、Viewer IDではない。ページの配列番号は並び替えで変わるため、将来の解析や再変換の永続識別子に流用しない。render.phpはget_block_wrapper_attributesを使用しており、単に現在のコールバックをショートコードから呼ぶだけでは、ブロック文脈・スタイル・アセット読み込みの整合を保証できない。

コマ設定・PC/スマホ別領域・専用モーダルに加え、通常ページの全画面表示、自由ズーム、パンを実装済み。コマ設定による拡大は作者が読ませ方を指定する機能、自由ズームは読者が任意に操作する機能として分離している。独立化の検査範囲とWordPress実機の未確認事項は[第1段階レポート](phase-1-report.md)を参照する。同レポートは当時の記録として維持し、今後の優先順位は本書を基準とする。

## 進める順番

### 当面の優先順位と区切り

直近はPhase 1.5〜2の実機検証と不具合修正に集中する。次に通常閲覧、漫画登録、コマ体験とCTAを順に整える。各段階で使える状態を確認してから次へ進み、将来候補をすべて完成させることを区切りにしない。

| 優先順 | その段階で完成させる最小範囲 | その時点では増やさないもの |
| --- | --- | --- |
| 1：安心して使える（Phase 1.5〜2） | 検証用WordPressで挿入・画像登録・保存・再読込・共存・更新を確認。方向操作、スマホ、コマ読みを含む重大な不具合を修正 | 新しい管理画面やブロック |
| 2：漫画を読みやすくする（Phase 3） | 通常ページの全画面、自由ズーム、パン。ページ送りとの競合を解消し、小規模試用を始める | 見開きの先行実装、縦読み・読書位置保存・先読みの全実装 |
| 3：漫画を登録して使い回す（Phase 4） | Libraryで登録・編集・保存し、表紙を見て1冊選ぶ。ブロックと1冊用ショートコードで表示。直接編集も維持 | 公開用の複数冊一覧、カテゴリー・シリーズ等の分類一式 |

Phase 5完了時を最初の商品範囲の見直し地点とする。ここで通常閲覧・登録・コマ読み・CTAの実用性を評価し、解析とAI相談用出力を初回販売へ含めるか、後続更新へ回すかを判断する。上記は開発の基本順序であり、Phase 6〜7の完成を販売準備開始の絶対条件にはしない。判断までは基本順序を維持し、販売開始や機能制限の導入は別途決定する。

Phase 3は全画面・自由ズーム・パンを整え、追加Aとして見開きを実装した。見開きは保存ページを組み替えず、縦長2ページを表示面として並べ、表紙・横長画像・余った最終ページは単独表示する。自動はViewer幅で切り替え、スマホ等の狭幅では1ページへ戻す。追加A-2では全画面のページ送りに限り、見開き構造のまま論理ページ順に1ページずつ大きく表示する`pageFocus`を追加した。通常のページ内Viewerと既定値は見開き全体表示として互換性を保つ。見開き専用ページめくりは追加B候補として実機確認後に判断する。縦読み・読書位置保存・先読み等の全候補完成はPhase 4の前提にしない。既存コマ読みの不具合修正はPhase 2から進め、Phase 5まで待たない。

2026-09-27時点で、Phase 3の最初の機能として通常表示の全画面ボタンを実装した。漫画ごとのオプションで既定OFFとし、既存投稿の表示を変えない。構文・PHP描画・PC/スマホ幅・ページ送り・専用ビューアーとの共存を自動検査し、専用テストサイトで全画面の終了ボタンと最終ページからの終了動作を確認した。

漫画ごとに既定OFFの自由ズームとパンを実装した。100〜300%の＋／−／全体表示、ピンチズーム、拡大中のマウス・1本指ドラッグ、キーボード操作に対応する。拡大中は画像上のページ送りを停止し、操作列の左右端に表示する小型三角を押した場合だけ、等倍へ戻して前後のページへ進む。通常のホイールは記事スクロールを維持し、`Ctrl`を伴うホイールだけをズームとして扱う。実機では引き続きタッチ操作、画面回転、各テーマでの画像寸法と操作競合を確認する。

全画面・自由ズーム・パンは、コマ設定を行わない漫画でも読者自身が文字を読みやすくするFree候補として扱う。専用ビューアーは作者がコマ位置・順序・倍率を準備し、読者が送るだけで読めるPro候補として区別する。両方を有効にした場合、全画面と専用ビューアーは同じ操作列にそろえ、通常時は専用ビューアー、全画面中は終了ボタンを大きくして優先順位を示す。α版では機能制限を実装しない。

Phase 2の専用ビューアーは、通常表示の閲覧位置に関係なく最初から読み始める動作を既定とする。制作者が漫画ごとに「現在のページから開始」を選んだ場合だけ、通常表示で開いているページに対応する最初のコマから開始する。既存投稿は既定動作を維持する。

Phase 4で共通の保存・参照・描画を整え、Phase 5のコマ改善・CTAを直接配置と登録済み漫画の両方へ反映する。Phase 6の解析ではManga Library登録済み漫画を正本とし、漫画と設置場所を区別する。Phase 7のAI相談用出力もLibraryの検証済み集計結果を利用する。この依存関係を基本の順序とする。

2026-09-27時点でPhase 4の基盤として、管理専用の`amv_viewer`投稿タイプ、1冊用ショートコード、表紙から1冊選ぶ「登録済みViewer」ブロックをローカル実装した。管理名は「漫画ライブラリ」。タイトル、既存AI Manga Viewerブロック、表紙画像、改訂履歴を保持し、新規登録時は既存ブロック1個を固定テンプレートとして開始する。投稿IDを安定したViewer IDとして一覧へ表示し、一覧から`[ai_manga_viewer id="123"]`をコピーできる。ショートコードまたは参照ブロックで保存済みViewerを表示し、参照ブロックの編集画面では選択後に表紙・公開状態・更新日だけを確認して選び直しと解除を行える。Viewer本文は展開せず、公開側で全体を描画する。公開用の個別URL・アーカイブは作らない。実機確認後に選択UIと公開状態の細部を調整し、複数冊一覧へは自動的に進まない。

Phase 5のCTAとして、任意ページに文字ボタンまたは画像を設定し、URL・別タブ・下部の左／中央／右を選ぶ基盤をローカル実装した。自由配置では画像上のドラッグ、座標、幅、文字サイズ、基本色、角丸を指定でき、一定間隔で光る演出とホバー演出も選べる。通常表示と全画面へ表示し、拡大中も画像と同じページ面として拡大・移動する。CTA上のタップはリンク、周囲のドラッグはパンとして分ける。専用コマビューアー内の表示とAnalyticsは実機確認後の段階へ残す。

Phase 6の最初の基盤として、Viewer・設置場所・ページ・CTAへ保存後も変わらない識別キーを追加した。登録済みViewerを複数箇所へ置いた場合は漫画の`viewerKey`を共通にし、参照ブロックごとの`instanceKey`で設置場所を分ける。キーが揃うViewerは、通常ページ送り、全画面、拡大、専用ビューアーによる最初の読書開始、利用モード、ページ初回到達、CTAクリックを`amv:reader-event`としてブラウザー内で通知する。同じ閲覧中の開始とページ到達を重複させず、読書開始前のCTA直接クリックは別区分にする。同一OriginのREST受信、許可リスト、レート制限、セッション・到達・イベントの保存、`eventId`重複排除までローカル実装した。解析収集は既定OFF。管理者向けON/OFF、30〜365日の詳細保存期間、日次削除、全データ手動削除、アンインストール時削除設定を追加した。ON/OFFはページキャッシュへ固定せず、キャッシュ対象外の設定RESTから取得する。文書表示中・Viewer表示中・直近90秒以内に操作あり、の条件を満たす有効閲覧秒数も最大30分まで保存する。匿名読者IDはサーバーでHMAC化し、同じブラウザー・Viewer・設置場所へ30分以内に戻った場合は同じ読書セッションとして再開する。今日・昨日・7日・30日・90日・全期間の漫画選択型レポート、主要KPI、最終到達ドーナツ、日別推移、読書進行、最大離脱、ページ到達、CTA内訳を追加した。任意期間、前期間との比較、漫画改善前後の比較、有効閲覧時間の中央値は将来候補であり、まだ実装しない。

Library一覧はPhase 4の登録・1冊参照を利用する将来機能とし、Phase 5〜8へ進む必須条件にはしない。Viewer IDと設置場所の識別だけは先に設計し、一覧が解析より先に完成しても後から計測を加えられるようにする。解析が先に完成した場合は一覧イベントを後から追加する。PDFや分類機能の完成を一覧表示の前提にしない。

## Gutenberg First, but not Gutenberg Only

通常は投稿内のGutenbergブロックで画像登録・並び替え・コマ設定を直接編集する。追加経路として、Phase 4で登録済み漫画の専用編集画面を設ける。一般的な設定ページに独自のエディターを組み込むのではなく、漫画用のカスタム投稿タイプ（CPT）の編集画面で既存ブロックを使う方針とする。編集機能を共用し、Classic Editor用に二重実装しない。

管理メニューは「AI Manga Viewer → 登録済み漫画／新規追加／設定」を候補とする。漫画をブロックで編集・保存してショートコードをコピーし、Classic Editorの記事へ貼り付ける。Gutenberg利用者も登録済み漫画を選択できる。投稿内の直接編集も維持し、すべての漫画に新規登録を強制しない。Analytics画面は後の段階で追加する。

Classic Editorを利用するサイトでも、Viewer編集画面だけでブロックエディターを使える構成を検証する。サイト全体でRESTやGutenbergが無効化されている場合まで自動的に対応できるとは扱わない。Classic Editorプラグインの設定による影響と、漫画用CPTだけブロック編集を有効にできる条件を実機検証し、対応範囲を明記する。別の編集GUIは初期範囲に含めない。

## 登録済み漫画の保存方式と再利用

Phase 2〜3で共通描画と識別方法への影響を確認し、Phase 4で実装する。CPTと既存ブロックを共用する方針を採用し、以下の比較はその判断理由として残す。投稿内の直接編集方式は維持する。

| 候補 | 長所 | 注意点・現在の評価 |
| --- | --- | --- |
| 投稿内block attributesを継続 | 現行データとGUIを維持できる | 投稿内の複数Viewerを安定したIDで外部参照しづらい。従来の直接編集には継続使用 |
| Viewer用CPT＋本文内block attributes | Viewer ID、一覧、編集、公開状態、リビジョンをWordPressの仕組みで管理しやすい。既存ブロックを再利用可能 | **採用方針**。Viewerを1つだけ置く制約、参照の循環防止、公開権限の設計が必要 |
| CPT＋構造化post meta | 共通データをPHP/RESTから扱いやすい | 入れ子スキーマ、登録、サニタイズ、権限、リビジョン、GUIとの同期を実装する負担。本文属性と全設定を二重管理しない |
| 同期パターン等のreusable entity | 既存の再利用・同期編集に乗れる | パターン管理UIや削除・公開仕様との結合が強い。Viewer専用の管理/参照制御に合うか要検証 |
| 独自テーブル | 大量データの検索・集計を専用設計できる | スキーマ更新、削除、復元、権限を自前で扱う。Viewer設定の初期保存先には採用しない。解析イベントは別途判断 |

登録済み漫画のCPTのpost_contentに既存の直接編集ブロックを1つ保存し、補助情報だけを必要に応じてmetaへ保存する構成とする。CPT、meta、attributesは排他的な選択肢ではなく、入れ物・補助情報・設定本体の役割を分ける。設定本体の正本を本文とmetaの両方に持たない。CPTのGutenberg/REST対応やリビジョンはWordPress標準APIを基本とする。[register_post_type公式資料](https://developer.wordpress.org/reference/functions/register_post_type/)

Gutenbergの保存済みViewer選択とショートコードは同じ正本を参照する。共有元の変更が全設置箇所へ反映されることをUIで伝え、個別変更が必要な場合は明示的な複製/独立化とする。旧投稿は自動変換せず、Viewer化は明示操作の候補に留める。

共通の「取得 → 検証・正規化 → 描画 → 必要アセット読込」を設計し、Gutenberg固有のwrapper処理は入口側へ分離する。公開ページでの出力は投稿タイプ・公開状態・閲覧権限を確認し、IDを知っているだけで下書きや非公開Viewerを読めないようにする。存在しないID、ゴミ箱、参照ループ、同一Viewerの複数配置、キャッシュ更新、アンカー/DOM ID重複を試験する。非公開Viewerにしただけで公開uploads内の画像/PDFが保護されるとはみなさない。

AnalyticsはViewer単位の集計と設置場所別集計を分け、ブロック/ショートコードで同じViewerを表示しても意図せず二重計測しない。ページの差し替え・並び替えでは対応関係と改訂を扱い、異なる内容の到達率を無条件に合算しない。読書位置保存も漫画と設置場所のどちらで共有するかを決め、編集時の一時的なclientIdを永続識別子として使わない。

解析対象はManga Library登録済みViewerだけとする。登録済みViewerは登録元の`viewerKey`を共有し、参照ブロックとショートコードの`instanceKey`で設置場所を区別する。直接配置Viewerの既存解析データは削除せず保持するが、新規イベント送信と管理画面集計から除外する。

## Manga Libraryの役割と管理情報

Manga Libraryは登録済みの漫画／Viewerを管理する中核機能とする。管理者向けのライブラリと、読者に公開する一覧ブロックを区別する。継続運用・再利用・解析・AI相談では登録方式を使用し、ライト利用向けの投稿内直接編集は表示機能として維持する。

| 情報 | 設計方針 |
| --- | --- |
| Viewer ID | 登録済み漫画の安定した参照キー。表紙画像の添付IDやブロックの一時IDと区別する |
| タイトル | 管理一覧、選択画面、公開カードに共通利用する |
| 表紙画像 | 重要な管理情報として明示指定できる案。1冊選択と一覧の基本サムネイルとして共用する |
| 更新日 | 管理・選択時に表示し、将来の更新順にも利用する。作品の改訂識別とは役割を分ける |
| 公開状態 | 初期から公開可否・閲覧権限の判定に必要。将来は一覧の絞り込みや管理表示との連携も検討する |
| 将来の連携情報 | カテゴリー、タグ、シリーズ、使用中ページ数、Analytics。分類の全実装を初期条件にしない |

「使用中ページ数」は漫画内の画像ページ数と、設置先の投稿・固定ページ数を混同しやすいため、実装時に名称と集計対象を決める。設置先数を扱う場合は一覧経由・ショートコード・重複配置を含む範囲を明示する。

### 表紙を見て選ぶUI

登録済みViewerの選択は、タイトルだけのプルダウンより「漫画ライブラリから表紙を見て選択」を有力候補にする。ブロック内の選択ボタンからライブラリ選択ダイアログを開き、表紙グリッド・タイトル・検索を基本とする。Viewer ID・更新日、表紙表示／リスト表示切替を追加候補にする。1冊表示は単一選択、一覧表示は複数選択と並び替えを扱う。同じ選択UIを共用する方針とする。

ライブラリ内のViewer検索と、表紙画像を指定するメディア選択は別の操作として設計する。選択結果にはViewer IDを保持し、表紙URLや漫画本文を各設置先へ複製しない。大量登録時は検索と分割取得を検討し、全Viewerの本体を選択画面で読み込まない。キーボード操作、選択状態、読めるタイトル、画像の代替テキストも検証項目とする。

表紙未設定時は「明示した表紙 → 漫画の先頭の有効なページ画像 → 共通プレースホルダー＋タイトル」を候補とし、削除済み画像や読み込み失敗も扱う。表紙を独立指定する利点と先頭ページ変更時の追従を比較し、最終仕様は実装時に決める。非公開作品のタイトル・表紙を公開一覧へ漏らさず、表紙情報も表示時に公開条件を確認する。

## Gutenbergのブロック構成候補

| ブロック名（仮称） | 役割 | 想定利用 |
| --- | --- | --- |

| 構成案 | 利点 | 注意点 |
| --- | --- | --- |
| 1冊表示と一覧表示を別ブロックにする（合計3種類） | 挿入時に目的が明確。単一選択と複数選択で設定を簡潔にでき、1冊表示を先に提供しやすい | ブロック一覧の項目が増える。似た名称による混乱や設定の重複を避ける必要がある |

現時点では**別ブロック案を第一候補**にする。直接作成・1冊表示・一覧表示の目的を分け、一覧の完成を1冊表示の提供条件にしないため。選択UI・カード・参照取得・描画処理は共用し、別々の編集エンジンを作らない。試作で挿入時の迷いと設定量を比較し、統合案のほうが分かりやすければ正式公開前に再判断する。

### 1冊表示の将来バリエーション

初期はViewerを直接表示する形を基本とし、将来は「表紙のみ」「表紙＋タイトル」「表紙＋『読む』ボタン」も検討する。表紙表示はクリックしてViewerを開く入口とし、一覧のカード表示と表紙情報・開く処理を共用する。これらの全バリエーションをPhase 4の必須条件にはしない。

## 将来機能：Manga Library一覧ブロック

初期案は「登録済みViewerを手動で複数選択し、任意順の表紙＋タイトルのカード一覧として表示」。漫画作品、採用漫画、商品紹介漫画、サービス紹介漫画、施工事例漫画の一覧を主な用途にする。会社案内資料・マニュアルの一覧にも利用できる余地を残すが、漫画の開発を遅らせる専用機能は追加しない。将来PDF等をViewerとして登録できる場合はカタログ・冊子・資料一覧へ広げられる構造を意識し、今回はPDF対応を再開しない。

将来の一覧条件は、手動選択、すべて表示、カテゴリー指定、タグ指定、シリーズ指定、新着順、更新順、任意順。初期は手動選択と任意順に絞り、分類検索や自動抽出は需要を確認して追加する。「すべて表示」でも一括無制限読込にせず、件数上限・ページ送り等を設計する。管理用の更新日は公開カードへの表示必須とはしない。

クリック時は次の方式を比較し、実装時に採否と初期動作を決める。登録しただけで公開のViewer専用ページが存在するとは仮定しない。

| 開き方 | 実装時の比較点 |
| --- | --- |
| その場で開く | 一覧の位置を保てる。展開時の高さ変化、閉じる操作、複数冊の同時展開を検討 |
| Viewerページへ移動 | URLを共有しやすい。公開ページまたは設置先URLの定義、一覧へ戻る導線が必要 |
| モーダルで開く | 記事から離れず読める。フォーカス移動・復帰、閉じる操作、スマホ、既存コマ読みモーダルとの競合を検証 |

一覧表示だけで全冊のViewerを起動せず、表紙カードと本体の読込を分ける。公開状態変更・削除後の除外、0件時の表示、画像欠損、レスポンシブ、複数一覧の設置、キャッシュ更新を検証する。選択できる権限と読者への公開可否を区別し、公開できないViewerは表紙・タイトルも出力しない。

### Analyticsとの将来連携

「一覧表示 → 表紙クリック → Viewer開始 → 最終ページ到達（読了の参考指標） → CTAクリック」を別イベントとして扱える構造を意識する。クリックだけでViewer開始とせず、最終ページ到達を実際の読了・理解の証明としない。CTAは任意ページに置けるため、この順序以外の経路もあり、一本道を強制しない。

Viewer IDを基準とし、設置ページ・一覧の設置箇所・カードの対象Viewer・内容改訂を区別できる方針を先に決める。一覧全体の表示と個々のカードが実際に見えたことの違い、重複計測、分母・計測期間を定義する。ページ移動で開く場合も出発元を関連付けられる設計を検討するが、閲覧者の永続追跡を前提にせず、同意・保存期間等は解析実装時に判断する。Viewer IDだけで利用者の一連の行動を復元できるとは扱わない。今回はイベント送信・保存・集計を実装しない。

## ショートコードによる互換表示

Phase 4では登録済み漫画の保存・参照仕様を先に整え、`[ai_manga_viewer id="123"]`形式の表示専用機能、その後にブロックから登録済み漫画を選ぶ入口を追加する。設定はGUIで編集し、pages・zoom・binding等を大量の引数で管理しない。登録・参照による基本表示はFree候補で、互換性をPro制限しない。

Classic Editor、Elementor、Bricks、Divi、WPBakery、ショートコード対応テーマ、PHPテンプレートからの利用を想定する。ただし各ビルダーが対応欄でショートコードを実行すること、CSS/JSが正しく読まれることは個別検証が必要。全製品互換を未検証のまま保証しない。

常時登録し、Viewer編集画面にコードとコピーボタンを表示する案を第一候補にする。登録だけで全ページにJS/CSSを読み込まない。ON/OFF設定は利用者の判断とトラブル要因を増やすため、明確な需要がなければ追加しない。OFFや無効化時に生のショートコードが残る問題も検討する。画像が見えるURLに変換するだけではなく、公開状態の確認を含む共通描画経路を使う。

一覧向けの`[ai_manga_library ...]`は将来候補に留め、現時点の必須対象にはしない。Gutenbergでは一覧ブロックを中心とし、Classic Editorで複数冊の一覧が必要という需要を確認してから追加を判断する。追加時は一覧ブロックと取得・公開判定・描画を共用する。

## 保留案：PDF Import / PDF対応の技術検証

方式比較・技術検証・実装とも当面保留し、着手Phaseは未定。PDFで用意した漫画の取り込み需要等が明らかになったとき、以下を再評価する。採用時の基本PDF利用はFree候補だが、提供を約束するものではない。会社案内・カタログ・フロアマップ・図面への用途拡張は現在の優先事項に含めない。

| 方式 | 利点 | 主な懸念 |
| --- | --- | --- |
| A: PDF.js等でPDFを閲覧時に直接描画 | PDFを入力として維持し、倍率に応じて再描画できる。文字選択やリンクを扱う発展余地 | ライブラリ/worker・メモリ・ブラウザー差・テキスト/注釈レイヤーの扱い。既存img描画とは別のページ描画処理が必要 |
| B: ページごとの画像へ展開して既存ページ系へ渡す | ページ送り・スワイプ・めくり・ズーム・全画面・CTA・解析・3モードを画像と共通化しやすい | 保存容量、変換時間、画質と倍率の上限。文字選択・検索・リンク・フォーム等のPDF機能は画像だけでは保持できない |

**Bを有力候補にするが、確定しない。** PDF.jsはA専用ではなく、ブラウザー内でページをcanvasへ描画して画像化するBの処理にも使える。「どこで変換するか」と「閲覧時にPDFか画像を扱うか」を分けて比較する。[PDF.js公式Getting Started](https://mozilla.github.io/pdf.js/getting_started/)、[公式描画例](https://github.com/mozilla/pdf.js/blob/master/docs/contents/examples/index.md)

### Bの実行環境と検証項目

| 検討項目 | 検証・判断内容 |
| --- | --- |
| ブラウザー側変換 | PDF.jsによるページ単位処理と生成画像のアップロード。Imagickを不要にできる一方、端末メモリ、タブ終了、モバイル、通信失敗、再開、アップロード権限・nonce・サーバー側検証が必要 |
| サーバー側変換 | Imagick、PDFデコードに関わるGhostscriptやポリシー、拡張の有無、時間/メモリ制限を検出。WordPressホスティング差が大きく、一律必須にしない。[WordPress Imagick実装](https://developer.wordpress.org/reference/classes/wp_image_editor_imagick/) |
| WordPressのPDF処理 | 標準のPDFプレビュー生成と全ページの取り込みは別。既存APIが使える範囲を実測し、全ページ変換が標準で保証されるとは想定しない |
| 大容量・ページ数・メモリ | 上限は未定。ページ数、ファイル容量、展開後ピクセル数、倍率ごとのメモリと所要時間を測る。全ページを同時にcanvas/画像へ展開せず、範囲指定・逐次処理・中断/再開を比較 |
| 画質・形式 | JPEG/WebP等の容量と文字/細線品質を比較。図面の高倍率、透明背景、回転、縦横混在を検証し、必要に応じてPNGも比較。PDF原寸の鮮明さが画像化で維持されるとは約束しない |
| 保存・メディア | 元PDFと生成画像をメディア添付として関連付ける案。元PDF ID、ページ番号、変換設定、改訂、生成物の所有関係を管理。元PDFの添付IDを画像idとしてそのままpagesへ入れない |
| 元PDF・削除 | 元PDFは初期案では保持。PDF削除時のViewer、生成画像削除時の表示、Viewer削除時の共有画像の扱いを決める。共有添付を連鎖削除せず、生成物の削除は影響を確認できる操作にする |
| 再変換・範囲指定 | 指定ページだけの取込、再変換結果の確認、成功後の差し替えと旧版復元。既存コマ/CTAはページ番号だけで新PDFへ移さず、対応関係や寸法変更を確認する |
| 失敗・特殊PDF | 暗号化/パスワード付き、破損、文字・リンク・注釈の欠落、途中アップロード失敗の扱いを決める。対応外を明示し、既存Viewerを壊さず失敗を報告する |

検証の成果物は対応サンプル、画質比較、実測負荷、環境条件、保存/削除/再変換仕様、採否理由とする。許容範囲が狭すぎる場合はPDFを延期し、画像の事前書き出しを案内する。外部変換サービスへの送信は初期案に含めない。

## Free / Pro製品境界

| 区分 | 確定した初期範囲 |
| --- | --- |
| Free | 直接配置Viewer、Manga Library、登録済みViewer、ショートコード、通常ページ送り、右綴じ/左綴じ、single/spread/auto、singleFirstPage、spread overview/pageFocus、全画面、全画面縦スクロール、zoom/pan、swipe、keyboard、coverLauncher、Library表紙、Direct → Library登録、軽量なページ切替 |
| Pro | コマ読み・専用コマViewer、PC/スマホ別コマ設定、CTA作成・自由配置・演出、AnalyticsとCTA計測、AI相談資料 |

通常漫画の公開はFreeで十分実用的にする。Proは作者が読ませ方を設計し、行動を促し、公開後の反応を分析して改善につなげる。漫画ライブラリの登録数制限は、利用者自身のサーバーへ保存する機能との相性が悪く、再利用という基本価値も弱めるため初期のFree/Pro境界には採用しない。ライセンス期限切れでは公開済みコマ読みとCTAを維持するが、新規作成・編集、Analytics閲覧、AI相談、更新、サポートを停止する。Analytics設定がONなら期限切れ中も計測・保存を続け、retention内データを更新後に再表示する。Pro停止・削除時は設定を保持したままFree Viewerへ安全にフォールバックし、新規計測を停止する。詳細は[Phase 8A仕様](phase-8-free-pro-design.md)を基準とする。0.3.0-alphaとPhase 8Bでは既存機能を削除・制限しない。

登録済み漫画とショートコードは開発対象に含めるが、販売時期と1.0の確定範囲は試用後に判断する。保留中のPDFは再開時も基本利用をFree候補として再評価し、現在の1.0の必須条件には含めない。

## CTAで合意した範囲

主に最終ページをCTA化するが、どのページにも配置できる。文字ボタンまたはメディアライブラリの画像を選び、URL・位置・サイズを指定する。ページ内の相対位置で表示し、コマ読みでもページと一緒に動く。見切れを避ける配置・コマ範囲は作成者が調整する。自動補正、画面への固定、専用の外側エリアは初期必須にしない。

Phase 8C-6でCTAを、Phase 8C-7で`panel_reader`をPro Add-onへ物理分離した。Coreは両Featureを既定で無効にし、公開markupと編集UIを出さない一方、`pages[].cta`、`focusAreas`、`mobileFocusAreas`と関連attributesの互換schema、正規化、ページ操作時の往復保持、Direct → Libraryコピーを継続する。Pro停止中にCoreで保存しても値を失わず、Pro再有効化時に復帰する。Freeの`pageFocus`はCoreへ残る。実装境界は[CTA物理分離](phase-8-cta-split.md)と[panel_reader物理分離](phase-8-panel-reader-split.md)を参照する。

## 将来候補：読者の「いいね」

漫画単位でON/OFFできる読者リアクションとして検討する。初期候補は合計数表示、同じブラウザーからの重複防止、解除可能な「いいね」。安定した集計キーが必要なため、最初はManga Libraryへ登録したViewer IDを対象とし、投稿内へ直接配置した未登録Viewerへの対応は識別方法を決めてから検討する。

実装時はREST APIの権限・nonce、匿名利用、キャッシュ環境、連打や自動送信への最低限の対策、削除時の集計データ処理、プライバシー説明を設計する。Analyticsと同じイベント基盤を共用できるか比較するが、単純な閲覧計測とは分けて管理する。現在のCTA・Manga Library安定化へは含めない。

## 技術上の判断

- 保存属性の互換性を優先し、旧CNI Blocksの自動変換を行わない。選択式transformは別途検証する。
- コマ拡大と読者の自由ズームは別機能として維持する。通常ページの全画面、自由ズームとパンは0.2.0-alphaで追加し、漫画ごとの設定で有効化する。
- 解析で「表示・到達」を「理解した・読み終えた」と断定しない。プライバシーと保存期間を実装前に決める。
- AI相談用出力は外部AI API接続なしで開始する。漫画の画像・あらすじがないと内容面の分析ができないことを明示する。
- Access Analytics Plusの設計を参考にできるが、必須依存にはしない。
- 演出の種類追加、見開き、Webtoon高度対応、GA4、自動AI検出は任意の将来候補。PDF、図面/フロアマップ専用対応は保留する。管理者向けManga Libraryと1冊参照はPhase 4、読者向けManga Library一覧ブロックはその後の任意拡張とする。専用の作品ポータルや分類機能一式の実装まで必須にはしない。
- ライセンス期限切れで公開済み漫画を突然変化させない。Proコードが有効なら既存コマ読み・CTA表示を継続し、制作・編集、Analytics閲覧、AI相談、更新、サポートを停止する。Analytics設定ONでは計測・保存とretentionを継続する。Pro停止・削除時はFree Viewerへフォールバックし、新規計測を停止して、Pro設定とAnalyticsを既定で保持する。

## Manga Library一覧と直接配置Viewerの登録導線

- Manga LibraryのWordPress標準投稿一覧を維持し、PCでは横型カード2カラム、1100px以下では1カラム、600px以下では表紙と情報を縦積みにする。
- 表紙領域は4:3とし、縦長・横長とも`object-fit: contain`で画像全体を見せる。表紙未設定時は同じ比率のプレースホルダーを表示する。
- カードにはタイトル、Viewer ID、ページ数、公開状態、更新日を表示し、編集、解析、ショートコードコピーを優先する。クイック編集、ゴミ箱、Clear Cache等の標準行操作は残す。
- 直接配置ViewerのInspectorから、現在のページ、PC／スマホ用コマ、CTA、表示設定を新規Manga Library Viewerへコピーできる。公開権限があれば公開、なければ下書きとして登録し、先頭ページの既存メディアを表紙候補にする。
- 元ブロックには`libraryViewerId`だけを追加保存し、再登録を防ぐ。登録後も直接配置ViewerとLibrary Viewerは独立し、自動同期しない。
- 登録成功後はLibrary編集画面、ショートコード、登録済みViewerブロックへの明示的な切替を案内する。切替を選ぶまで元ブロックは変更しない。
- 直接配置Viewerは登録後もAnalytics対象にならない。登録済みViewerブロックまたはショートコードとして配置したLibrary Viewerだけを計測する。

## Version方針

Phase 8C-8でCore所有の`AI Manga Viewer 設定`を追加した。製品状態、Manga Library、解析設定、Free / Pro Feature状態をまとめる軽量なハブとし、Analytics専用の`解析設定`とは分離する。Proは公開フィルターとFeature APIを通じて状態を提供し、Phase 8DのLicense / Updater UIを後から追加できる構造にした。正式URLが未確定のマニュアル・サポート・公式サイトリンクは表示しない。詳細は[一般設定画面](phase-8-general-settings.md)を参照する。

Version変更は利用者の明示指示があるときだけ行う。ZIP生成では変更しない。本体ヘッダーを取得元としreadmeのStable tagを一致させる。

1.0以降は互換性を壊す変更がmajor、互換性を保つ機能追加がminor、不具合修正がpatch。0.x開発中も保存データの互換性を軽視せず、機能追加と修正を区別して履歴に記載する。

alphaは開発・検証中、betaは主要機能が揃って試用中、rcは対象範囲を固定した公開候補。プレリリースを区別する場合はalpha.1、beta.1、rc.1等を使い、配布先の比較動作も検証する。同じ版のZIPの置換はローカル試験に限定し、外部へ配った版は内容を識別できるよう管理する。
